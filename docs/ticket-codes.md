# Stable ticket codes

Each new ticket gets exactly one random 32-byte base64url code. `publicTokenHash`
remains its unique SHA-256 lookup value. `encryptedPublicToken` is a required
AES-256-GCM ciphertext. Free booking and Stripe fulfillment write both in the
same transaction as the ticket. Encryption errors abort that transaction; there
is no plaintext fallback, backfill, or automatic code replacement.

## Configuration and storage

Set the **server-only** environment variable `TICKET_CODE_ENCRYPTION_KEYS`:

```dotenv
TICKET_CODE_ENCRYPTION_KEYS='{"active":"k1","keys":{"k1":"<base64-encoded 32-byte random key>"}}'
```

Generate a new independent key locally (do not paste its output in logs/issues):

```powershell
node -e "process.stdout.write(require('node:crypto').randomBytes(32).toString('base64'))"
```

Use standard padded base64, not a password or AUTH_SECRET-derived value. Store
the keyring in your secret manager and separately protected disaster-recovery
backup; never commit it, use NEXT_PUBLIC_, or send it to clients. Missing keys
cannot be recovered from the hash. Both app and background fulfillment workers
need the same keyring. Configuration is read lazily, so builds need no real key.
If using the existing Compose setup, the operator must explicitly forward this
variable into the app container's environment; merely adding it to an env file
does not extend Compose's environment whitelist. No live deployment settings
are changed by this patch.

Ciphertext envelope: `v1.<key-id>.<iv>.<tag>.<ciphertext>`; the last three fields
are canonical base64url. IV = 12 random bytes, authentication tag = 16 bytes.
The authenticated additional data binds purpose, version, key ID and ticket hash.
After decryption the code's format and SHA-256 are checked again. Unsupported
formats, missing keys and authentication failures stop the operation with safe
reason codes (`CONFIG`, `FORMAT`, `KEY_UNAVAILABLE`, `AUTHENTICATION`), without
logging key material, ciphertext or code. Never enable request-body capture on
ticket APIs, RSC responses, server actions, scanner calls, or SMTP payloads.

## Access and email

Only the authenticated booking owner can fetch their code via `getMyTicket`.
Foreign/unknown IDs both produce 404; missing login redirects to login. The code
is supplied to the owner's QR renderer, not the shared public display DTO.
Public links remain `/tickets#<code>`; the fragment is POSTed to the protected,
rate-limited, no-store public endpoint and is not included in server access logs
or referrers. The API returns display data, never stored ciphertext or code.

The scanner now accepts only this 43-character random code and resolves its
SHA-256 hash. The retired `account.*` credential is not supported. Current
permissions, status checks and atomic check-in updates still determine admission.
Displaying, resending, cancelling or redeeming does not replace a ticket code.

The owner can explicitly resend all tickets of a confirmed booking from the
ticket page. The server selects the original booking recipient (no client-supplied
recipient) and decrypts stored codes. Limit: five requests per user per 15-minute
window. SMTP failure returns a safe retry message. Like the original free-booking
mail, explicit resend is synchronous, not a new durable outbox; retry uses the
same codes. It never resets/overwrites a Stripe outbox lock or sent marker.

The initial Stripe mail remains atomically queued with tickets in `PaymentMail`.
Its existing encrypted payload and retry/locking behavior are unchanged, including
the existing AUTH_SECRET-derived *mail* encryption. The new long-lived *ticket*
encryption is independent. Already queued messages retain their identical links
during retries and key rotations. The separate outbox AUTH_SECRET rotation rules
in `docs/stripe.md` continue to apply. No Wallet implementation was found.

## Migration and disposable old test data

Migration `20261028140000_stable_ticket_codes` adds a required column without a
default. It succeeds on an empty Ticket table and intentionally fails if old
hash-only tickets exist. No codes can be reconstructed for these rows. Neither
the migration nor application deletes data or invents replacements.

No database was queried, reset or migrated for this change. Before deploying,
the operator should check ticket count and pending checkout/mail jobs. Old
confirmed bookings, tickets and sent/pending ticket emails form one disposable
test dataset: do not delete only ticket rows while retaining confirmed bookings
or old ticket-mail payloads. They will not be regenerated by repeated fulfillment.
Stop the test app/workers first and discard old Stripe test sessions/events that
could replay against the fresh database. Old emails and QR screenshots are invalid.

For a **disposable local development database only**, a full reset is the simplest
consistent cleanup. It removes ALL local application data (users, companies,
events, bookings, tickets, payments and outboxes), then reapplies all migrations.
This explicit example targets the local database from `.env.example`, overriding
any external `.env`/`.env.local` URL. Verify that localhost:5432 is your disposable
local Postgres, not a tunnel to a remote database. Run manually in PowerShell:

```powershell
$env:DATABASE_URL = 'postgresql://postgres:postgres@localhost:5432/event_management'
npx prisma migrate reset --force
```

If the ticket table is already empty and no stale ticket mail/bookings exist,
no reset is needed. After configuring the new keyring, apply migrations manually
with `npx prisma migrate deploy` against the intended environment and deploy the
new app/workers together. Preview cleanup must be separately approved/performed
by the operator; do not run the local reset against a remote/production database.

## Key rotation without code rotation

1. Generate a new independent key `k2`. Deploy a keyring containing **both** k1
   and k2 everywhere, initially with `active: "k1"`.
2. After every reader has both keys, switch `active` to k2. New ciphertext uses
   k2; readers continue decrypting k1 rows. Keep both keys during rollout.
3. In an operator-only server maintenance job, page through Ticket records by ID.
   For each old-key row, call `decryptTicketCode(oldCiphertext, publicTokenHash)`
   and then `encryptTicketCode(sameCode, publicTokenHash)` with k2 active.
   Update **only** encryptedPublicToken using an optimistic compare-and-swap:
   `updateMany({ where: { id, encryptedPublicToken: oldCiphertext }, data: {
   encryptedPublicToken: newCiphertext } })`. Use bounded batches/transactions,
   validate decryption before writing, stop on errors, log only counts/IDs/reasons,
   and never print payloads. Do not call createTicketToken, modify the hash or
   ticket status. This is resumable; already-k2 rows can be skipped.
4. Verify all rows decrypt under k2 and none reference k1. Stop old writers before
   declaring completion. Only then remove k1 from the live keyring. Retain old
   keys in secure backup for database backups that still contain old ciphertext.

An automated rotation command is intentionally not exposed to app users. This
procedure changes encryption only: QR values and email links remain identical.
Code revocation/replacement and an Apple Wallet integration are separate work.
